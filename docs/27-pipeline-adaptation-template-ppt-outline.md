# 27 · Dagster Pipeline 適配與 Template 化：主管匯報 PPT 大綱

> 用途：向主管報告「將既有 Pipeline 放入 Dagster 執行，並以 Pipeline Template 提供更多使用者接入」的工作成果與下一階段規劃。
>
> 建議時長：30 分鐘主體、15 分鐘 Q&A。
>
> 最後更新：2026-10-30。

---

## 27.0 匯報目標

這份簡報不需要從 Dagster 的產品介紹開始，而是讓主管在有限時間內確認以下三件事：

1. **方向可行**：既有 Pipeline 可以接入 Dagster，核心演算法不需要重寫。
2. **方法可複製**：成功經驗可以沉澱成 Pipeline Template，讓其他使用者按標準流程接入。
3. **投入有邊界**：平台、Pipeline 團隊與業務使用者的責任清楚，風險與下一階段決策明確。

整份簡報的核心主張：

> **我們不是重寫 Pipeline，而是替它加上一層可治理、可觀測、可複製的執行控制面。**

建議在開場、Demo 結束與結尾各回到這句話一次。

---

## 27.1 敘事主線

簡報依序回答以下問題，不要從 Asset、Resource、Sensor 等技術名詞開始：

```text
現況痛點
  → 現有 Pipeline 已能成功接入
  → Dagster 補上執行、觀測與治理能力
  → 把接入方法固化成 Template
  → 更多使用者可以自助接入
  → 用權責邊界與 CI 控制風險
  → 需要主管核准試點與下一階段資源
```

主管關心的順序通常是：

```text
業務價值 → 風險 → 誰負責 → 要投入多少 → 何時看到結果
```

技術細節放在附錄，只有被追問時才展開。

## 27.4 各頁展開

### 第 1 頁：封面

建議標題：

> **從既有 Pipeline 到可複製的 Dagster 平台**

副標：

> 既有 Pipeline 適配、Template 化與規模化推廣

頁面只保留一句結論：

> 縮短新 Pipeline 從開發到上線的週期，同時提升可靠性與可追溯性。

---

### 第 2 頁：為什麼現在要做

不要先介紹 Dagster，先用日常事故說明問題：

- Pipeline 散落在個人環境或排程工具中，沒人確定今天是否成功執行。
- 某一步失敗後，只能翻日誌猜測失敗位置。
- 修正一筆資料也必須整條 Pipeline 重跑，浪費時間與運算成本。
- 下游發現資料缺欄位時，上游才知道品質有問題。
- 不同團隊各自安裝依賴，升級時互相影響。

這一頁的管理訊息：

> 問題不是「Pipeline 能不能跑」，而是「能不能穩定、可重複、可追溯地跑」。

---

### 第 3 頁：目標與驗收標準

建議列三個目標：

1. **現有 Pipeline 可運行**：保留核心邏輯，在 Dagster 端到端執行。
2. **Template 可複用**：新 Pipeline 不必重新實作排程、重試、測試與部署。
3. **使用者可自助接入**：按標準流程完成開發、驗證與上線。

驗收條件建議包括：

- 可由排程、事件或人工觸發。
- 執行狀態、日誌與產出物可查詢。
- 失敗後可重試，資料可精準補跑。
- 產出物具有血緣與版本資訊。
- 品質不合格時可阻止下游產出。
- 新 Pipeline 可通過 CI 契約檢查。

量化目標應在試點前先量測 Baseline，再設定階段目標。

---

### 第 4 頁：一頁式解決方案

建議使用四層架構圖：

| 層次 | 內容 | 保留或新增 |
| --- | --- | --- |
| 既有 Pipeline | 領域邏輯、演算法、模型呼叫、業務規則 | 保留 |
| Dagster 適配層 | Asset、Job、Resource、Schedule、Sensor、Check | 新增 |
| 平台能力層 | 執行環境、儲存、告警、權限、成本治理 | 平台提供 |
| Pipeline Template | 專案骨架、標準元件、測試、CI、部署與文件 | 標準化 |

一句話解釋：

> 把每個團隊重複做的事情抽到平台，把各 Pipeline 特有的邏輯留給開發者。

---

### 第 5 頁：現況與目標的差異

| 面向 | 現況 | 目標 |
| --- | --- | --- |
| 執行 | 手動觸發或零散排程 | Schedule、Sensor、Automation |
| 可觀測性 | 主要依賴 Log | Run 歷史、資產血緣、狀態與耗時 |
| 恢復 | 常需全量重跑 | 分區補跑與精準回填 |
| 品質 | 人工抽查 | Asset Check 與發布門檻 |
| 接入 | 各自建置 | Template 與標準化路徑 |
| 治理 | 依賴個人經驗 | 權責、CI 契約與版本管理 |

管理訊息：

> 這次工作不是把一支腳本搬進新工具，而是把一次性經驗變成可複製能力。

---

### 第 6 頁：既有 Pipeline 的接入方法

建議畫成四步法：

1. **盤點**：確認入口、步驟、輸入輸出、設定、外部依賴與失敗處理。
2. **建立最小鏈路**：先讓一條可驗證的 Pipeline 端到端跑通。
3. **包裝與接線**：將既有程式包成 Asset，接上平台 Resource、儲存與觸發機制。
4. **產品化**：補上 Check、重試、測試、CI、部署與文件。

技術選型可放附錄：

- Python Pipeline：優先 Asset 化。
- CLI、腳本或容器化 Pipeline：使用 Dagster Pipes 保留原有執行邊界。
- 核心演算法不需要為了接入 Dagster 而重寫。

---

### 第 7 頁：Pipeline 元件如何映射到 Dagster

| 既有 Pipeline 元件 | Dagster 對應 |
| --- | --- |
| 執行入口 | Asset、Job 或 GraphQL 觸發 |
| 處理步驟 | Asset 與依賴關係 |
| 設定與密鑰 | `ConfigurableResource` 或平台 Resource |
| 檔案與資料表 | IO Manager、Object Store URI 或 metadata |
| 資料驗證 | Asset Check |
| 定時與事件 | Schedule、Sensor、Automation Condition |
| 執行結果 | Run event、Log、Asset metadata |
| 外部程序 | Dagster Pipes |

建議用一條真實 Pipeline 的流程圖示範，例如：

```text
輸入 → 清洗 → 轉換 → 驗證 → 輸出
```

再標示每一步是哪個 Asset、使用哪個 Resource、在哪裡做 Check。

---

### 第 8 頁：可靠性、可觀測性與成本控制

| 控制點 | 要說明的價值 |
| --- | --- |
| 分區與回填 | 只重算失敗或受影響的資料 |
| 失敗重試 | 區分可重試、不可重試與需人工介入的錯誤 |
| Asset Check | 不合格產物不往下游發布 |
| 血緣與 Metadata | 追蹤輸入、產出、程式版本與執行時間 |
| Code Location 隔離 | 不同團隊使用獨立映像與依賴 |
| 併發池與限流 | 保護資料庫、模型服務與外部 API |
| 用量紀錄 | 按 Pipeline、租戶或分區歸集成本 |

必須主動說明限制：

- 非冪等操作不能直接重跑，需要補上去重或覆寫策略。
- 老舊腳本可能把設定寫死在程式中，需要先抽離。
- 外部服務失敗不代表 Dagster 本身故障，告警要能正確分流。

---

### 第 9 頁：成果展示

建議現場 Demo 四件事：

1. 展示 Asset Graph 與上下游血緣。
2. 觸發一次執行，展示狀態、耗時與歷史紀錄。
3. 展示單一分區失敗後的重試或補跑。
4. 展示 Check 失敗阻止下游產出。

Demo 話術：

> 這個畫面不是任務列表，而是可交付產物的狀態台。每一個節點都能回答它是什麼、從哪裡來、什麼時候更新、是否通過品質門檻。

Demo 前必須準備：

- 使用脫敏但接近真實的資料。
- 預先完成大部分執行，避免現場等待。
- 預留一個失敗或灰色分區用於補跑。
- 預先錄屏，環境異常時直接播放。
- 不現場寫程式、不現場排錯、不逐行念 Log。

---

### 第 10 頁：Pipeline Template 包含什麼

Template 的定位不是範例程式，而是新 Pipeline 的標準生產線。

建議包含：

- 專案骨架與 `Definitions` 入口。
- Asset、Resource、Partition、Check 的標準範例。
- 設定檔、環境變數與密鑰注入規範。
- 本地開發、測試替身與單元測試。
- CI 契約檢查與 Definition 驗證。
- Code Location 部署設定與註冊流程。
- README、接入指南、版本與升級說明。
- 一個可端到端執行的最小範例。

Template 也必須有：

- 明確 Owner。
- 版本號與相容性策略。
- Issue 與支援管道。
- 破壞性變更的遷移窗口。

管理訊息：

> Template 要能降低接入成本，也要能被維護與升級，否則只會變成另一份沒人敢改的範例。

---

### 第 11 頁：使用者的標準接入流程

建議畫成 Golden Path：

```text
建立專案
  → 設定平台 Resource
  → 實作業務 Asset
  → 補上 Check 與測試
  → 本地驗證
  → CI 契約檢查
  → 平台註冊 Code Location
  → 部署與驗收
```

每一步都要標示：

- 誰負責。
- 輸入與輸出。
- 完成條件。
- 失敗時找誰。

自助化不等於完全放權。使用者可以自行開發與測試，但生產環境註冊、基礎設施資源與平台配置仍由平台團隊控制。

---

### 第 12 頁：平台與 Pipeline 使用者的權責邊界

| 類別 | 平台團隊 | Pipeline 團隊 |
| --- | --- | --- |
| 影響範圍 | 整個 Dagster 實例或所有 Pipeline | 自己 Pipeline 的業務正確性 |
| 主要責任 | 實例、執行環境、儲存、權限、監控、Template 版本 | 業務邏輯、資料品質規則、測試、模型與 Prompt 版本 |
| 可修改 | 平台配置、Resource、SDK、註冊表 | 自己的 Asset、Check、測試與 Resource wiring |
| 不應修改 | 不應繞過平台契約 | 不應修改別人的 Code Location 或平台基礎設施 |

建議隔離方式：

> 一個團隊 = 一個 Code Location = 一個映像 = 一份 `Definitions`。

共享介面只保留在：

- 平台 SDK。
- Resource 名稱與契約。
- Asset 命名與必要 Metadata。
- 分區鍵與標籤規範。

用 CI 與 CODEOWNERS 固化規則，不要依賴口頭協調。

---

### 第 13 頁：落地路線

| 階段 | 目標 | 主要交付物 | Exit Criteria |
| --- | --- | --- | --- |
| 一、試點 | 一條既有 Pipeline 端到端跑通 | 最小 Pipeline、Demo、問題清單 | 可觸發、可追蹤、可補跑 |
| 二、Template 化 | 把接入方法標準化 | Template、平台 SDK、CI、部署文件 | 第二個使用者不需改平台核心即可接入 |
| 三、規模化 | 建立長期營運能力 | 註冊、版本、監控、成本、支援機制 | 接入流程可重複且風險可控 |

每一階段都要有明確 Gate，不要一次承諾所有功能。

---

### 第 14 頁：成效指標

| 類別 | 指標 |
| --- | --- |
| 接入效率 | 新 Pipeline 平均接入時間、Template 使用率 |
| 穩定性 | 執行成功率、失敗恢復時間、重複事故數 |
| 品質 | Check 通過率、不合格產物攔截率 |
| 成本 | 全量重跑次數、單次執行成本、增量節省比例 |
| 採用度 | 活躍 Pipeline 團隊數、從 Template 建立的 Pipeline 比例 |

建議格式：

| 指標 | 目前 Baseline | 第一階段目標 | 量測方式 |
| --- | ---: | ---: | --- |
| 接入時間 | 試點前量測 | 待設定 | PR 建立到正式運行的時間 |
| 執行成功率 | 試點前量測 | 待設定 | Dagster Run 歷史 |
| 平均恢復時間 | 試點前量測 | 待設定 | Incident 開立到恢復 |
| 重跑成本 | 試點前量測 | 待設定 | Run metadata 或帳單 |

---

### 第 15 頁：風險、資源請求與決策

| 風險 | 可能影響 | 緩解措施 |
| --- | --- | --- |
| 適配範圍失控 | 試點拖長、無法驗收 | 先做最小可運行鏈路 |
| Template 無人維護 | 使用者各自複製貼上 | 指定 Owner、版本與支援機制 |
| 使用者繞過平台資源 | 密鑰外洩、環境無法遷移 | CI 契約檢查與 CODEOWNERS |
| 老舊 Pipeline 不具冪等性 | 重跑造成重複資料 | 納入適配評估與回填限制 |
| 平台成為上線瓶頸 | 接入排隊 | 自動驗證與標準註冊流程 |
| 模型或外部 API 成本失控 | 預算超支 | 併發池、限流與用量 Metadata |

建議向主管提出三項具名決策：

1. 核准一條試點 Pipeline 與其業務 Owner。
2. 配置平台與 Pipeline 團隊的投入人力。
3. 核准試點環境、成功指標與下一階段 Gate。

結尾回到：

> 先證明既有 Pipeline 能穩定接入，再把接入方法產品化成 Template。

## 27.6 Q&A 附錄

### Q1：為什麼選 Dagster，而不是 Airflow 或自行寫排程？

> 我們的目標不只是定時執行任務，而是管理可交付產物。Dagster 以 Asset 為中心，能直接回答產出物從哪裡來、哪一版程式產生、是否通過品質檢查、重跑會影響哪些下游。若自行寫排程，調度、重試、事件紀錄、血緣與 UI 都要另外實作。

### Q2：這是不是把既有 Pipeline 全部重寫？

> 不是。核心演算法與業務邏輯保留，主要新增的是宣告、執行邊界、資源接線、品質檢查與排程。對於 CLI 或容器化流程，也可透過 Dagster Pipes 接入。

### Q3：Template 和平台 SDK 有什麼差別？

> Template 規定專案怎麼建立、怎麼測試與部署；平台 SDK 提供 Resource、IO、分區與測試替身等共用能力。Template 依賴 SDK，但兩者都有自己的版本與 Owner。

### Q4：多個團隊使用會不會互相影響？

> 每個團隊使用獨立的 Code Location、映像與依賴。共享面主要是平台 SDK 與 Resource 契約，透過版本與 CI 控制相容性。

### Q5：使用者需要學 Dagster UI 嗎？

> Pipeline 開發者需要了解基本的 Asset、Run、Partition 與 Check；一般業務使用者應透過既有業務介面使用，不需要接觸 Dagster 的內部名詞。

### Q6：Dagster 掛掉會不會造成資料丢失？

> Dagster 是控制面，不是資料面。已落在外部儲存或資料庫的產物不會因控制面重啟而消失；恢復後可以重新排程或補跑。

### Q7：成本怎麼控？

> 使用固定併發池與限流，支援分區增量重跑，並把模型版本、執行時間與用量記到 Run 或 Asset Metadata。後續再建立按 Pipeline 與租戶的成本看板。

### Q8：怎麼避免 Template 變成沒人維護的展示程式？

> Template 必須有 Owner、SemVer、CI、範例測試與升級政策。每次平台能力變更時，先把 Template 升到相容版本，再開放給使用者。

### Q9：如何衡量這次工作成功？

> 同時看四類指標：接入效率、執行穩定性、資料品質與使用成本。試點前先量 Baseline，再設定第一階段目標，而不是只在驗收時主觀判斷。
